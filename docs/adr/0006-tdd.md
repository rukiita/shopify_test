# 0006. Develop with TDD and merge PRs with merge commits

- Status: Proposed
- Date: 
- Issue: #22 (DEC-7)

## Context

The task asks for regular commits, which suggests the process is evaluated alongside the code.
The core logic (`order-mapper` / `should-overwrite` / `normalize-tag` / `build-csv`) consists of pure functions that are easy to test first.
On the other hand, Shopify configuration and scopes cannot be verified by tests, and how to test Polaris Web Components is still unknown (ADR-0002).

## Options considered

1. Full TDD, including the UI
2. TDD for domain, repositories and routes; UI and configuration excluded
3. Write tests after the implementation

## Decision

Option 2.

- Domain (pure functions): TDD without mocks
- Repositories: TDD against a test SQLite database. Mocking Prisma would hide drift between the mock and the real thing
- Routes: mock only `authenticate.*` and `admin.graphql`
- GraphQL responses are not invented: a spike captures real responses as fixtures before TDD starts
- UI follows the outcome of ADR-0002. Configuration is verified by hand and documented in the README

To keep a visible TDD trail, commits are split as `test:` → `feat:` → `refactor:`, and PRs are merged with merge commits.

## Consequences

- Positive: test names map to the spec numbers of each requirement, so the issue's test list, the tests and the implementation form one line. The commit history alone explains the process
- Negative: more commits and a longer history on `main`. Red commits leave failing tests, so `git bisect` needs to skip them
- Revisit when: UI tests turn out to be practical (extend to option 1)
