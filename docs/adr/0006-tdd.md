# 0006. Develop with TDD and merge PRs with merge commits

- Status: Proposed
- Date: 
- Issue: #22 (DEC-7)

## Context

The task asks for regular commits, which suggests the process is evaluated alongside the code.
The core logic (`order-mapper` / `should-overwrite` / `normalize-tag` / `build-csv`) consists of pure functions that are easy to test first.
On the other hand, Shopify configuration and scopes cannot be verified by tests, and how to test Polaris Web Components is still unknown (ADR-0002).

## Options considered

1. Full TDD, including the UI
2. TDD for domain, repositories and routes; UI and configuration excluded
3. Write tests after the implementation

## Decision

Option 2, organized as a double loop.

**Outer loop (one per requirement issue).** Start each issue with one failing acceptance test at the
route level that states the acceptance criterion as seen from outside (e.g. "a signed `orders/create`
webhook stores the order"). It stays red while the inner loop runs, and turns green when the issue is done.

**Inner loop (one per test-list line).** Red → Green → Refactor on the domain and repositories until
the outer test passes.

How each layer is tested:

- **Domain (pure functions):** no mocks; inputs and outputs only
- **Repositories:** a test SQLite database. Mocking Prisma would hide drift between the mock and the real thing
- **Routes:** run with `testConfig()` from `@shopify/shopify-app-react-router/test-helpers`, enabled by
  the `SHOPIFY_TESTING` environment variable. Webhook requests in tests are signed with the test secret,
  so `authenticate.webhook` verifies them for real instead of being mocked. Only `admin.graphql` is replaced
- **Shopify API boundary:** queries are typed with `@shopify/api-codegen-preset` (`graphql-codegen`), so a
  query that asks for a field the schema does not have fails the type check. Responses used in tests are
  real responses captured in a spike and saved as fixtures. Types guard the query; fixtures guard the mapping
- **Not covered by TDD:** UI (follows ADR-0002), configuration (`shopify.app.toml`, scopes) and the real store
  end to end. These are checked by hand: `shopify app webhook trigger` for a first check of a route, then real
  actions in the development store, and documented in the README

To keep a visible TDD trail, commits are split as `test:` → `feat:` → `refactor:`, and PRs are merged with merge commits.

## Consequences

- Positive: each issue's acceptance criterion exists as an executable test from the start. Test names map to
  the spec numbers of each requirement, so the issue's test list, the tests and the implementation form one line.
  Signature verification is tested with the real code path, and query mistakes surface at type-check time
- Negative: setup in Step 1 grows (test config, a signing helper, codegen). Route tests are the slowest to
  write, and they come first. More commits and a longer history on `main`; red commits mean `git bisect` must skip them
- Fallback: if signed requests cannot pass `authenticate.webhook` under `testConfig()`, mock `authenticate.webhook`
  as originally planned and record it here
- Revisit when: UI tests turn out to be practical (extend to option 1)
